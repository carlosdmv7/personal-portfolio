Job Market Intelligence Engine

An end-to-end ELT + LLM enrichment pipeline for relocation-friendly job search.

01 The problem

Searching for jobs abroad as an EU relocator is noisy: postings live on dozens of boards, few clearly state whether they offer visa sponsorship, and there's no easy way to spot trends across the market. I wanted a system that aggregates postings, flags sponsorship, and lets me ask questions in plain English — built entirely on free infrastructure so it costs nothing to run.

03 Key decisions & why
  • DuckDB + MotherDuck instead of a cloud warehouse — the dataset is medium-sized and the priority was €0 running cost. DuckDB gives warehouse-grade SQL locally; MotherDuck's free tier hosts the shared copy. Same dbt project runs against both, so dev and prod stay identical.
  • A pluggable LLM provider — the enrichment flow abstracts the model behind one interface so it can run on local Ollama (free), Gemini, or Claude. That keeps the pipeline free by default and swappable when quality matters more than cost.
  • dbt medallion (staging → integration → marts) — raw API payloads are messy and overlap across sources. Isolating cleaning (stg), cross-source dedup (int), and business marts (facts/dims) makes each layer testable and the lineage obvious.
  • Text-to-SQL over the gold layer, not the raw data — the "Ask the Data" agent queries curated marts, so natural-language questions hit clean, well-named columns and return trustworthy answers instead of guessing over raw tables.

05 What I'd do differently now
I'd formalize evals for the visa classifier (a labelled golden set + accuracy tracking) instead of trusting the LLM output as-is; replace ad-hoc dedup with an explicit surrogate-key strategy in the integration layer; add dbt exposures to map which marts feed which Streamlit page; and move scheduling off my machine onto a managed runner so ingestion doesn't depend on my laptop being on.

Spanish Housing Radar

Finding under-priced property listings with a benchmark-driven Opportunity Score.

01 The problem

Spotting a genuinely under-priced flat means comparing it against the right peers — same neighborhood, similar size — not a city-wide average. Doing that by hand across portals is impractical. I wanted a pipeline that ingests listings continuously and scores each one against local benchmarks, so a good deal is quantified, not a gut feeling.

03 Key decisions & why
  • Scrapfly instead of raw scraping — property portals have aggressive anti-bot protection. Outsourcing proxy rotation and rendering to Scrapfly kept the extractor simple and reliable, so I could spend effort on modeling rather than fighting blocks.
  • Idempotent upserts on ingest — listings reappear across daily runs. Upserting on a natural key means re-running a flow never creates duplicates, which keeps benchmarks honest.
  • A hierarchical Opportunity Score — the score is a z-score of €/m² against a benchmark, but a single flat needs enough comparables to be meaningful. So it falls back neighborhood → district → city until it has ≥8 comparables, and flags low-confidence scores instead of hiding them.
  • Medallion bronze/silver/gold in dbt — raw listings (bronze), deduplicated + typed (silver), benchmarks + scores (gold). Every business rule lives in version-controlled SQL with tests, not in the app.
 gold/opportunity_score.sql
-- z-score of price/m² against the local benchmark
select
    listing_id,
    price_per_sqm,
    (price_per_sqm - benchmark_median_ppsqm)
        / nullif(benchmark_stddev_ppsqm, 0) as opportunity_z,
    benchmark_grain   -- neighborhood | district | city
from {{ ref('int_listings_benchmarked') }}

Every PR is validated against an isolated CI schema (ruff, pytest, dbt build), so changes to scoring logic can't silently break production data.

05 What I'd do differently now
Coverage is still growing, so most listings currently benchmark at city grain. I'd prioritize backfilling history so neighborhood-level scores become the default, switch the gold models to incremental materializations instead of full refresh as volume grows, and add explicit freshness tests + scraping SLAs so stale data is caught automatically.

Enterprise KPI Platform

From manual Excel trackers to a governed, automated reporting platform across 20+ plants.

01 The problem

A global manufacturer tracked operations KPIs manually in Excel. Each region calculated metrics differently, so executive summaries didn't reconcile — Finance in one continent reported different numbers than Operations in another, and monthly reviews stalled while people argued about whose figures were right. There was no shared definition, no ownership, and no single source of truth.

02 Key decisions & why
  • Governance before automation. Before building pipelines, I established a KPI contract — definition, owner, calculation rule and source — for 130+ metrics. Automating an ambiguous KPI just produces wrong numbers faster.
  • A Streamlit intake app, not more spreadsheets. Some inputs and targets are genuinely manual. Rather than fight that, I built a governed intake app (Streamlit on AWS) so manual data enters through one validated door instead of scattered files.
  • Unify third-party sources in the warehouse. Operational, safety/EHS, HR and ERP data lived in separate third-party systems. I landed them in Snowflake and modeled governed views (with dbt for modular SQL) so every region computes KPIs from the same tables.
  • Optimize the whole refresh path, not one tool. The bottleneck spanned Streamlit → Snowflake → Power BI. Tuning the models, incremental logic and the semantic layer together is what delivered the step-change, not any single fix.
