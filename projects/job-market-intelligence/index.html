Job Market Intelligence Engine

One question, every morning: which open data roles in the EU are asking for my stack? Five free APIs, an LLM that reads each posting, a dbt medallion on MotherDuck — and a rule that a posting nobody has read yet is never reported as a miss.

The problem

Looking for a data role in the EU means reading the same posting three times on three boards and still not knowing the thing that decides whether it's worth applying: which technologies does it actually ask for, and do I have them? Boards index on title and location, which are the two fields that tell you least.

So the pipeline reads for the stack instead. Five free APIs are collected into an append-only log every morning, an LLM reads each posting for the technologies it names, the seniority and the language you'd need to work in it, and a dbt medallion turns that into one canonical row per posting. On 19 Sep 2026 that was 767 open data roles across five markets from 596 companies — Spain the largest at 229, then Germany 190, the Netherlands 178, Sweden 132 and 38 remote.

The constraint that shaped everything was a free tier of 20 LLM requests a day, which made partial coverage the permanent state rather than a bug to hide. One rule carried the whole app through it: a posting the model hasn't read says "not yet classified" on every surface, never "no match." Conflating the two would invert the meaning of every screen.

That backlog is now cleared — every open role has been read — and the rule matters more, not less. Only 47% of them yield a tech stack, and the reason is no longer the quota. It's how much text the boards publish, which is a different problem with a different answer, so the app names which of the two you are looking at instead of reporting one number.

Key decisions & why

  • Batched the LLM eight-fold on the same free quota, and matched responses by an echoed index. The 429 body names the quota it enforces: GenerateRequestsPerDayPerProjectPerModel, value 20. Counted in requests, not tokens — so one posting per call was spending the whole day's budget on round trips. Ten postings now ride in each request, and 23 enrichments a day became 180; coverage went from 33% of open roles to all of them, a backlog of roughly six months cleared in under three weeks. The catch is that a batched response can come back short or reordered, which would attach one job's stack to another silently, so every result echoes the index of the posting it answers and is matched on that — never on position.
  • A chart that looked like a market fact turned out to be an artefact of the source. With the queue cleared, only 47% of open roles yielded a stack — so the leftover gap had to be something other than the quota. It was the boards. Measured per source: Adzuna, which supplies all of Spain, Germany and the Netherlands, returns a ~500-character teaser; JobTech returns the full ~4,000-character ad. The same classifier reading both finds ~0.7 technologies in one and ~7.9 in the other. So "Sweden asks for dbt more than Spain does" was never a finding — 91% of Swedish roles are stack-matchable against 30–39% of Dutch, German and Spanish ones, and that is a property of what gets published, not of the market. "Roles we can stack-match" is now a headline KPI on every market rather than a footnote, and the stack chart carries an explicit warning against cross-market comparison. ADR 0011.
  • Facts with an authoritative source are looked up, never inferred. Where a question has a register behind it, the project joins against the register and shows the receipt; the LLM is reserved for what only exists as prose. Visa sponsorship is the worked example, because it's the one field where both are available for the same question: every employer is cross-referenced against the official IND register of recognised sponsors — 12,797 Dutch employers, 12,793 of them carrying a KvK number you can check by hand. That lookup surfaced a gap no text-reading model could find: 34% of employers on the Dutch local corpus are recognised sponsors against 3% on the remote-first boards (108 of 322 vs 175 of 5,296) — and it holds for postings the LLM has never seen. It renders inside the Netherlands market page and nowhere else, because that is exactly what it is: a property of the one tracked market that publishes a machine-readable register.
  • The classifier is validated without hand labels, against a signal it is never shown. english_sufficient is the model's reading of the prose. detected_language — the language the ad is written in — is derived deterministically on ingest and kept out of the prompt. One GROUP BY over both, across every posting the model has read: of 643 English ads it says English suffices for 85%, of 255 Dutch ads for 0.4% — one posting. Full coverage for the price of one query, against the ~30 a hand-labelled set would have reached in the same time — and the separation is the evidence: a model pattern-matching on job titles would answer the same way whatever language the ad was in. It is reported as agreement between two independent signals, never as an accuracy score, because neither column is ground truth. The hand labels were spent on the visa target instead, where they were the only instrument available — and where they retired the feature.
  • The flagship feature was retired on its own evidence. Visa sponsorship was the original pitch. Across 730 enriched postings the classifier's output was unclear 583 times and explicit_yes once; the first 14 hand labels scored 0.000 precision on that class. Not a failing model — a class with no support in the corpus, and no amount of further labelling changes it. So the product axis moved to stack fit and the feature was demoted to a showcase rather than deleted — and then, six days later, demoted again: it had been left in the top navigation behind a passport icon, which made a five-market app look like a Dutch relocation tool. ADR 0007 records the measurement and the reversal; ADR 0011 records the second one, including the sentence from the author that triggered it — "es que no entiendo muy bien el objetivo." When the person who built a page can't say what it's for, no visitor will work it out. Eleven ADRs in the repo are written this way.

# would then write one job's stack onto another — silently, and with no

    seen.add(item.index)
    enrichments.append(self._to_enrichment(postings[item.index - 1], ...))

Supporting detail

  • A filled role is not an open one. Boards delete filled roles rather than closing them, so "days since we last saw it" is the only liveness signal that exists. It becomes an is_active flag measured against the corpus's newest observation, never current_date — otherwise a stalled pipeline would mark the whole market closed on a calendar technicality. Before the flag existed, 1,331 of 2,755 data roles hadn't been seen in three weeks and were still being offered as current.
  • Stack scoring is two-tier, and the expensive tier is opt-in. Tier one intersects your CV with the technology vocabulary the LLM already extracted from real postings and ranks every open role by pure set arithmetic — no API call, whole corpus, instant. Tier two spends one LLM call on the single posting you pick. The CV lives in st.session_state only: never written to the warehouse, a file or the logs, and gone when the tab closes. The scoring functions are pure and unit-tested, with no Streamlit import.
  • DuckDB + MotherDuck instead of a cloud warehouse — the dataset is medium-sized and the priority was €0 running cost. The same dbt project runs against local DuckDB and MotherDuck's free tier, so dev and prod stay identical. A pragmatic call for this scale, not a claim about production architecture.
  • Text-to-SQL over the gold layer, with the guarantee on the connection. The "Ask the Data" agent sees only the marts schema — raw and staging are never exposed to the prompt — and is limited to a single SELECT with a forced LIMIT 500. Three of those four guardrails are checks in this repo's own code; the fourth is a read-only connection MotherDuck enforces server-side, which is where it belongs, since the free plan issues read/write tokens only. The generated SQL is always displayed before it runs. It is guard-railed, not hardened against a hostile user, and the app says so.

A reproducible pipeline: uv for envs, ruff/mypy/pytest in CI, and dbt tests as data contracts — so a broken source fails loudly instead of silently corrupting the app. Model and test counts are read from the project's own manifest.json; the sponsor-register size is the row count of the scraped seed; the coverage and market figures are the warehouse's own, measured 19 Sep 2026.

Honest status

As of September 2026: the dbt medallion, the Pydantic contracts and the IND cross-reference are production-grade. Coverage is stated everywhere rather than rounded up — every open role has now been read, but only 47% yield a parsed stack, and the app names which of those two numbers you are looking at. Ingestion breadth is a demo: five free sources are a fraction of the real market, since LinkedIn and Indeed sit behind paid anti-bot services. Ingestion depth is uneven and now measured per market, because three of the five run on a source that returns a teaser instead of the ad. Prefect is instrumentation, not a deployment — the flows carry @flow decorators and would report to Prefect Cloud if the env vars were set, but a hosted worker isn't free, so the scheduler is a GitHub Actions cron. There is no Docker: the Compose scaffolding couldn't be built or tested on the dev machine, so it was deleted rather than left standing as an untested claim. And no accuracy percentage is claimed for the classifier — it is cross-checked against an independent deterministic signal at full coverage, plus a golden set whose one completed measurement retired a feature.

What I'd do differently now

I'd have profiled the sources before trusting a single cross-market chart. One query — average description length per board — was sitting there the whole time, and it would have shown that comparing Spain's stacks to Sweden's was comparing a teaser to a full ad. Same lesson as the flagship: a day of counting first would have saved both reversals, and ADR 0007 and 0011 are good documents about costs that measuring earlier would have avoided. Beyond that: widen ingestion, because five free sources bound every conclusion the project can draw; add dbt exposures so the lineage says which marts feed which Streamlit page; harden the canonical clustering, which still leans on normalised company and title rather than an explicit surrogate-key strategy; and move the scheduler onto a worker the day this stops needing to be free.
